TCP connection

from the article

“Before your browser can send a HTTP request though, it first needs to establish a TCP connection with the Web server.” — all it says.

beyond the article

TCP gives two programs an ordered, reliable stream of bytes. Whatever one side writes comes out the other side in the same order.

Four things identify a connection: both addresses and both port numbers. Your browser never chose its own port — the operating system handed it one.

The programming interface for this is a socket. Part 3 of this series takes sockets apart properly.

HTTP request

GETmethod path HTTP/1.1version

from the article

“The HTTP request consists of the line indicating the HTTP method (GET, because we are asking our server to return us something), the path /hello that indicates a “page” on the server we want and the protocol version.”

beyond the article — the other page names

The article only ever asks for /hello. The other names are ours. They are not invented though: each was really sent to the server on this page, and the reply you see is the one that really came back.

beyond the article — other methods

GET asks for something. POST sends data, PUT replaces, DELETE removes, HEAD asks for the top part only. This server never looks at the method — DELETE gets the same reply, which was checked by sending it.

beyond the article — other versions

1.0 opened a new connection per request. 1.1 keeps it open for reuse. 2 is binary and interleaves many requests over one connection. 3 runs over QUIC, on UDP, instead of TCP. This server writes HTTP/1.1 but closes after one response — which is 1.0 behaviour.

beyond the article — this server was changed

The article's own webserver1.py answers “Hello, World!” to everything. Its reply is a fixed string written into the code, and the path is never looked at. That was checked by really sending it 24 different page names: one reply came back, byte for byte, every time.

The server here has one line added — it looks up the path before answering — so that you can see the page name actually decide something. Everything else is the article's code.

That is what the path is for: MDN calls it “the path to the resource on the Web server”, and RFC 9110 says “the target of an HTTP request is called a resource”, identified by the URI. A server that ignores it, like the article's, is the unusual one.

from the article

“The response consists of a status line HTTP/1.1 200 OK, followed by a required empty line, and then the HTTP response body.”

beyond the article — other status codes

The first digit gives the family: 1xx information, 2xx it worked, 3xx look elsewhere, 4xx the request was wrong, 5xx the server broke.

You have just produced two of them. RFC 9110 says 200 means the request succeeded and a representation of the resource is included; 404 means the server “cannot find a current representation for the target resource”. Ask for /cats and the server tells you so in the status line, before the body says a word.
