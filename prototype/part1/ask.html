Have you ever wondered how a website works underneath?

You type an address, a page comes back. Here is the whole of it, drawn with two circles, a line and a dot.

ASKING FOR

The line — a TCP connection

It opens before anything is sent, and both dots travel along it.

FROM THE ARTICLE

“Before your browser can send a HTTP request though, it first needs to establish a TCP connection with the Web server.” — all it says.

BEYOND THE ARTICLE

TCP gives two programs an ordered, reliable stream of bytes: whatever one side writes comes out the other side in the same order.

Four things identify a connection — both addresses and both port numbers. Your browser never chose its own port; the operating system handed it one.

The programming interface for this is a socket. Part 3 of this series takes sockets apart properly.

The dot going out — the HTTP request

GETmethod path HTTP/1.1version

FROM THE ARTICLE

“The HTTP request consists of the line indicating the HTTP method (GET, because we are asking our server to return us something), the path /hello that indicates a “page” on the server we want and the protocol version.”

BEYOND THE ARTICLE — THE OTHER PAGE NAMES

The article only ever asks for /hello. The others are ours, but not invented: each was really sent to the server behind this page, and the reply you see is the one that really came back.

BEYOND THE ARTICLE — OTHER METHODS

GET asks for something. POST sends data, PUT replaces, DELETE removes, HEAD asks for the top part only.

FROM THE ARTICLE

“The response consists of a status line HTTP/1.1 200 OK, followed by a required empty line, and then the HTTP response body.”

BEYOND THE ARTICLE — OTHER STATUS CODES

The first digit gives the family: 1xx information, 2xx it worked, 3xx look elsewhere, 4xx the request was wrong, 5xx the server broke.

You have produced two of them. RFC 9110 says 200 means the request succeeded and a representation of the resource is included; 404 means the server “cannot find a current representation for the target resource”.

The circle on the right — the web server

A program waiting on port 8888. It reads the request, prints it to its own terminal, and sends a response back down the same line.

BEYOND THE ARTICLE — THIS SERVER WAS CHANGED

The article's own webserver1.py answers “Hello, World!” to everything. Its reply is a fixed string in the code and the path is never looked at — checked by really sending it 24 different page names, which produced one reply, byte for byte, every time.

The server here has one line added: it looks up the path before answering, so the page name can decide something. That is what a path is for — MDN calls it “the path to the resource on the Web server”, and RFC 9110 says “the target of an HTTP request is called a resource”.

Every reply here really came back: each page name was sent over a real connection to a real running server — the article's webserver1.py with one line added so the path decides the answer. Notes headed BEYOND THE ARTICLE go further than it does.
